# 房东模拟器更新路线图

> 这份文档是后续开发的总清单。它不代表所有项目都要同时开工，而是用来防止功能遗漏、方向跑偏和界面再次缩水。

## 一句话目标

把现在的“公寓经营角色卡”升级为一个以**装修、招募和跨世界租客碰撞**为核心，可以逐步接管公寓、医院、写字楼、旅馆、飞船等不同建筑的“房东经营模拟系统”。

正文继续负责故事和爽感；经营界面负责复杂操作；AI负责创意生成和语义理解；代码负责状态、规则、空间、联动和可视化。四者各做自己擅长的事。

## 一、已经完成，后续不得倒退

### 1. 仓库与角色卡工程化

- 已建立独立本地项目和公开 GitHub 仓库。
- 原始 PNG、JSON 角色卡已经进入仓库管理。
- 已支持从 PNG/JSON 拆解角色卡，并重新打包生成可导入的 PNG 角色卡。
- 角色卡名、世界书名按版本生成唯一名称，避免 SillyTavern 同名冲突。

### 2. 酒馆助手脚本多合一

- 仓库内继续保留一个个独立源脚本，方便维护。
- 发布时可以构建为单个酒馆助手脚本。
- 已有“在线版”：单脚本通过 jsDelivr 加载固定版本的构建产物。
- 已有“离线版”：完整代码直接嵌入单脚本。
- 目前 22 个启用模块已经完成迁移，没有遗漏原有启用功能。
- 原来的脚本切换器已由统一运行时接管，不再作为业务模块迁移。
- 大富翁和原来已禁用的重制实验脚本不属于本轮迁移范围。

### 3. 原版界面和美化

- 正文美化、悬浮菜单、掌上公寓、手机、微信、天气、新闻、地图、音乐、租客资料、创意工坊等原有启用界面已经恢复。
- 现有布局、CSS、美化效果和交互是后续开发的视觉基线，不能为了重构而换成简陋占位界面。
- 已做真实 SillyTavern 的在线版、离线版冒烟测试，并验证 CDN 加载。

### 4. 当前工程底座

- 已有模块清单、依赖顺序、统一启动、错误隔离、生命周期和基础服务注册机制。
- 已有统一 MVU 事务写入、校验、状态订阅和当前会话经营回溯；更广泛的旧脚本兼容层与自动修复仍待后续补全。
- 已有 MVU 2.0 Zod 模型、三栋基础建筑样例、建筑界面编译器和本地/AI 双模式任务中心。
- 已有四频道联动队列、逐步感知、租客统一身份和建筑数字孪生底座。
- 已有自动构建与回归检查；当前基线测试为 106/106 通过。

### 5. 0.2.0-preview.3 已完成的多建筑第一切片

- 公寓作为初始总部，医院和写字楼作为带基础格局的接管候选。
- 新增独立“房东经营中枢”，包含资产总览、当前建筑、建筑接管、装修、招募和动态记录。
- 接管、装修和招募都采用“生成预览 → 玩家选择 → 确认写入”，确认前不会污染 MVU。
- 医院接管、旧住院部装修、跨世界人物招募可以完全使用本地模拟数据跑通。
- 新界面具备明亮/暗色主题、窄屏适配和减少动画模式；旧有 22 个启用模块继续原貌保留。
- 本轮真实 SillyTavern 验收没有发送消息，也没有调用真实 AI。

### 6. 0.3.0-preview.1 已完成的 Landlord OS 底座

- 统一任务中心支持本地/AI 提供器、排队、取消、超时、重试和确认写入。
- 经营变化可以进入正文、微信、新闻和建筑四个独立消费队列。
- 四频道草稿已接上原有微信和新闻接口，但仍要求玩家显式点击投递。
- 感知度真正决定楼层和房间显露程度，探索操作可以逐步补全信息。
- 租客的头像键、联系人 ID、建筑标记和位置使用统一身份。
- 数字孪生开始以可计算布局呈现各楼层空间，可直接点击进入装修。

### 7. 0.3.0-preview.2 已完成的交互与安全层

- 数字孪生支持楼层聚焦、空间详情、人物占用、装修入口和可视化相邻连线。
- 接管、装修、招募和探索进入当前会话操作链，可安全撤销、重做并检测重叠更新冲突。
- 联动队列支持单条或同频道批次预览，确认前不会调用任何投递端口。
- 正文联动使用酒馆助手一次性提示词注入，微信和新闻继续写入原有模块。
- 每次发布继续使用独立角色卡名、世界书名和产物文件名，避免 SillyTavern 名称冲突。

### 8. 0.3.0-preview.3 已完成的装修具现化与空间同步

- 装修方案中的配色、材质、照明和家具会被编译为确定性的视觉令牌，同一个方案在装修中心、数字孪生和详情面板中保持同一种观感。
- 材质不再只是一行描述：木质、玻璃、金属、石材、织物、柔软、自然和超自然风格拥有不同纹理与光影表现。
- 叙事—空间同步中枢可以为人物移动生成本地提案，并区分同层路线、跨楼层、跨建筑、未知空间和结构冲突。
- 人物移动采用“校验 → 提案 → 玩家确认 → 原子写入”，同时维护人物位置、房间占用、感知状态和正文/建筑联动事件。
- 若正文或其他模块已在确认前改动人物位置，旧提案会转为冲突，不会覆盖更新后的剧情状态。

### 9. 0.3.0-preview.4 已完成的建筑运行脉冲

- 装修、设施、空间用途和真实在场人物会实时编译为舒适体感、功能兑现、生活活力与空间吸引四类运行指标。
- 指标是从 MVU 状态确定性派生的体验镜像，不是新的财务负担，也不会制造强制维修、倒计时或失败惩罚。
- 不同组合可以激活“人屋共鸣”“设施 × 装修”“世界碰撞”和“社交引力”等建筑协同效应。
- 系统会从真实建筑状态中寻找可玩的今日舞台；玩家先选择预览，再确认点亮，不会自动替玩家推进剧情。
- 点亮后会更新参与人物状态、建筑今日亮点、建筑记忆和四频道草稿，并进入可撤销的经营操作链。

### 10. 0.3.0-preview.5 已完成的租客具身生活

- 人物会根据职业、性格、来源世界和内心线索形成自己的空间偏好，不再共用一条笼统满意度。
- 同一个房间对不同人物会产生不同契合度、具体反应和“房间已经回应了哪些偏好”的解释。
- 引擎会比较当前建筑中的真实空间，给出比当前位置更契合的去处及分数差，而不是凭空推荐不存在的房间。
- 两位以上人物处在同一空间时，会生成带有明确建筑和房间定位的共同生活相遇。
- 人物感受仍采用选择、预览、确认边界；确认后写入 MVU 人物生活状态，并生成正文、微信和建筑草稿。
- 若确认前人物已经移动，旧反应会失效，不会把上一间房的感受错误写到新位置。

### 11. 0.3.0-preview.6 已完成的数字孪生传感叠图

- 同一套建筑坐标新增“空间结构、运行体感、租客感受”三种即时切换图层。
- 空间结构层继续呈现装修材质、家具标记、相邻连接和感知范围。
- 运行体感层把建筑脉冲压回具体房间，以热力、综合分和传感条显示哪里高光、哪里仍在蓄能。
- 租客感受层只高亮真实有人居住的空间，并在房间节点和详情面板显示人物契合度与具身反应。
- 三层图使用同一份 MVU、同一份房间 ID 和同一套确定性布局，不会维护容易错位的重复地图数据。

### 12. 0.3.0-preview.7 已完成的剧情移动意图提取

- 空间同步页可以粘贴剧情片段，本地解析“谁走进了哪个真实房间”，不再要求所有移动都手动点选。
- 本地解析只接受角色卡状态中已经存在的人物名、建筑名和空间名，不认识的内容进入待辨认，不猜造 ID。
- 本地规则只对明确的移动词生成提案；单纯在文字里提到房间不会擅自改变人物位置。
- 显式 AI 模式使用 Zod/JSON Schema 提取结构化意图，只发送玩家粘贴的片段与可用 ID 索引，不自动读取聊天历史。
- 无论来自本地还是 AI，提取结果都必须再经过建筑路线、接管状态和并发位置校验，最后由玩家逐条确认。
- AI 模式未由玩家开启时，即使宿主存在生成接口，也会在请求开始前硬性阻止调用。

### 13. 0.3.0-preview.8 已完成的下一回合上下文胶囊

- 当前建筑的空间、运行体感、人物位置、具身反应和近期已确认变化可以压缩为一份小型正文上下文。
- 胶囊只读取当前建筑，不会把其他候选建筑、整份 MVU、界面缓存或未确认提案全部塞进提示词。
- 编译器具有严格字符预算并显示 token 估算；信息过多时按空间、人物、事件顺序安全截断。
- 玩家可以查看实际 XML 内容，确认前不会调用正文注入接口。
- 确认后使用酒馆助手 `injectPrompts` 以 once / system / depth 0 注入下一次生成，不会常驻污染后续上下文。
- 胶囊明确告诉 AI 不得替玩家确认经营操作，也不得把未知空间和待确认提案写成既成事实。

### 14. 0.3.0-preview.9 已完成的关系火花

- 只有真实占用同一建筑、同一空间的两个人物才会产生关系火花，单靠正文提及不会建立关系。
- 引擎综合来源世界、职业、性格、空间舒适度和空间活力，为相遇生成可解释的潜力与标签。
- 关系分数用于呈现爽点与差异，不会每日衰减，不会制造强制社交失败或经营惩罚。
- 玩家必须先选择、再确认；人物已经离开相遇空间时，旧火花会失效，不能覆盖新的空间状态。
- 确认后关系会原子化地双向写入两个人物，并创建正文、微信和建筑三类联动草稿。
- 关系卡沿用租客具身生活的视觉语言，显示双方视觉身份、相遇地点、推演理由和已有关系。

### 15. 0.3.0-preview.10 已完成的关系星图

- 当前建筑内的人物会被编译为 SVG 网络节点，节点颜色、身份和所在空间全部来自同一份 MVU。
- 相同空间形成可见群落；人物移动后节点会自动进入新的空间群落，不保存容易过期的第二套坐标数据。
- 待确认关系火花显示为流动虚线，确认后的双向关系显示为发光实线。
- 已确认关系不会因为人物暂时分开活动而消失，跨房间仍能在星图中保留连接。
- 星图同时显示人物数、生活空间数、已确认关系、潜在火花和跨世界连接数。
- 修复经营中枢长页面主网格不能正确收缩的问题，租客页及其他内容较长页面恢复内部滚动。

### 16. 0.3.0-preview.11 已完成的双人生活导演台

- 只有已经确认的人物关系才会解锁双人生活场景，潜在火花不能直接跳过关系确认。
- 场景根据双方来源世界和职业差异生成“跨世界共居实验”“双职业联手”等专属方向。
- 目标空间来自当前建筑真实空间，并优先选择双方现处空间或运行状态更好的共同舞台。
- 启动前会再次校验两个人的实时位置；任意一人被其他剧情移动后，旧编排会自动失效。
- 确认后在一次 MVU 事务里同步双方位置、房间占用、人物状态、建筑亮点和活跃度。
- 每次双人生活生成正文、微信和建筑草稿，但不把私人共同生活强行写进公共新闻。
- 关系动作从主控制器拆为独立模块，控制器保持在 500 行架构红线以内。

### 17. 0.3.0-preview.12 已完成的空间记忆叠图

- 数字孪生新增“空间记忆”第四图层，与空间结构、运行体感和租客感受共用同一套房间坐标。
- 已确认事件按照建筑 ID 和空间 ID 回灌到具体房间，建筑级事件不会被错误塞入任意空间。
- 关系场景、关系火花、建筑场景、装修、入住、人物感受和移动拥有不同回声权重与主题色。
- 房间节点显示回声数量、主导事件类型和记忆强度；没有事件的房间自动降低饱和度。
- 详情面板按最近发生顺序显示事件标题、摘要、参与人物和发生时间。
- 图层完全从现有事件列表派生，不新增需要玩家维护的存档字段，也不调用 AI。

### 18. 0.3.0-preview.13 已完成的租客自主行动

- 当前建筑中的人物会根据职业、性格、内心线索和空间运行状态提出自己的下一步生活行动。
- 摄影师、灵植师、治疗师和记录类职业拥有不同的行动文案与空间偏好解释。
- 提案会选择建筑中真实存在且不同于当前位置的空间，不会猜造房间 ID。
- 自主行动不是自动执行：选择阶段只改界面，玩家批准后才进入 MVU 事务和经营回溯链。
- 确认前再次比对人物实时位置；其他剧情已经移动人物时，旧自主提案无法覆盖新状态。
- 成功后同步人物位置、旧房间和新房间占用、职业化活动状态以及正文/建筑联动。
- 公共模板工具被拆为独立模块，主模板回到 461 行，控制器保持在 500 行架构红线以内。

### 19. 0.3.0-preview.14 已完成的多建筑人员调度

- 空间同步目标不再局限于当前建筑，而是汇总总部与全部已接管建筑的可见空间。
- 每个目标明确显示建筑、楼层、房间、空间类型和“当前建筑/跨建筑”标记。
- 选择状态同时使用建筑 ID 和空间 ID，避免不同建筑出现同名或同键空间时选错目标。
- 本地路线会明确区分建筑内移动、跨楼层通行和跨建筑交通，并在确认前显示理由。
- 未接管建筑与未知空间不会进入可选列表；手动伪造目标仍会被路线服务拒绝。
- 确认后继续使用原子位置与占用同步；人物被其他剧情移动时，旧跨建筑提案同样会进入冲突。

### 20. 0.3.0-preview.15 已完成的经营版图神经网络

- 资产总览会从同一份建筑状态即时编译总部、已接管建筑和待接管机会，不保存第二套版图数据。
- 总部作为网络核心，已接管建筑通过发光实线形成运营交通，待接管建筑通过流动虚线形成机会链路。
- 接管确认后，对应节点和链路无需额外写入就会自动从“机会”升级为“运营中”。
- 建筑节点显示空间数、活跃度、接管状态与当前焦点，点击仍复用原有进入建筑或查看提案流程。
- 版图汇总已接管建筑数、运营链路、接管机会和人物总数，并跟随真实状态变化。
- 未发现建筑不会进入网络；暗色主题、窄屏布局和减少动画偏好均有独立适配。

### 21. 0.3.0-preview.16 已完成的装修全息投影

- 玩家选中装修方案后，方案会直接投射到目标空间所在的真实数字孪生楼层。
- 投影保留楼层中其他空间和已知连线，目标房间使用方案材质、配色、照明和家具视觉令牌高亮。
- 侧边对照同时展示当前状态与确认后的视觉，不再依赖文字想象装修差异。
- 投影纯粹从当前孪生数据和候选方案派生，不新增 MVU 字段，也不会在选择阶段修改存档。
- 不存在的建筑空间会被拒绝，不允许投影引擎凭空猜造房间。
- 确认后仍复用原有原子装修事务、事件联动和经营回溯，预览层不复制业务写入逻辑。

### 22. 0.3.0-preview.17 已完成的候选人入住预演

- 选定候选人与安置空间后，系统会临时模拟其进入真实房间，再即时丢弃模拟状态。
- 预演复用建筑脉冲与租客具身引擎，显示个人空间契合、具身反应、房间和整栋建筑的脉冲增量。
- 目标空间已有其他人物时，预演会列出真实室友，并计算候选人与他们可能形成的关系火花。
- 新人物可能激活的世界碰撞、人屋共鸣等建筑协同会在确认前显露。
- 未知空间、未接管建筑和已经存在的人物 ID 都不能创建入住投影。
- 确认前不会写入人物、占用、关系或事件；正式加入继续使用原有原子事务与经营回溯。

### 23. 0.3.0-preview.18 已完成的建筑接管结果预演

- 选定接管方向后，系统会在状态副本中运行建筑身份变换，展示确认后的名称、主题、简介和今日亮点。
- 待接管节点如何升级为已接管节点、机会虚线如何升级为运营实线，会在确认前直接显示。
- 预演对比接管前后的感知度、可见楼层与空间、已接管建筑数和运营链路数。
- 经营方向中的标签、可玩机会和新显露空间集中进入结果面板，不需要在长段文字里寻找变化。
- 预演和正式接管共用同一个建筑身份变换函数，避免两条逻辑随版本演化后出现偏差。
- 确认前原 MVU 保持“可接管”；确认后才创建接管事件并切换当前建筑。

### 24. 0.3.0-preview.19 已完成的跨建筑经营态势雷达

- 每栋已接管建筑都使用舒适、功能、活力和吸引四个维度绘制即时雷达图。
- 雷达卡同时显示综合脉冲、人物、来源世界、空置空间和已激活协同，方便横向比较。
- 系统从真实空间中找到当前最有成长余地的位置，并给出装修、设施或人物安排建议。
- 总览汇总已接管建筑、版图人物、来源世界、可塑空间与活跃协同，并标出最高脉冲建筑。
- 所有建议只用于发现爽点和下一处可玩位置，不产生账单、失败、倒计时或强制任务。
- 可接管和未发现建筑不会混入雷达统计，也不会影响全局焦点判断。

### 25. 0.3.0-preview.20 已完成的跨建筑人才匹配矩阵

- 每个版图人物会与所有已接管建筑中充分感知的真实空间进行契合评估。
- 契合度复用职业、性格、来源世界、装修、设施、用途和同屋人数，不另造一套假规则。
- 矩阵按人物并排各建筑最佳空间，显示当前落点、全局最佳、契合分和可解释匹配标签。
- 只有换到另一栋建筑后分数真正提升的组合才进入“人物流动机会”。
- 匹配引擎不修改 MVU、不调用 AI、不自动搬人；真正移动仍要由玩家进入空间调度中心确认。
- 感知不足的楼层和空间不参与投影，避免黑科技反过来破坏逐步感知。

### 26. 0.3.0-preview.21 已完成的 24H 跨建筑生活流线

- 从每个人物当前所在的真实空间出发，编译当前落点、白日主场、晚间碰撞和夜间归处四个时段。
- 白日主场偏重职业契合与空间功能，晚间碰撞偏重活力、舒适、吸引和公共空间。
- 沙盘复用人才契合矩阵的全空间投影，并通过原有空间路由引擎校验每段建筑内、跨楼层或跨建筑通行。
- 建筑人流波形按四个时段统计每栋建筑的投影人数，且每个时段都必须与现有人物数守恒。
- 演算鼓励在近似最优的空间中形成不同时段落点，避免整天原地不动，但不会为了多样性强制选择明显不合适的空间。
- 流线只读且不会自动执行；玩家仍可进入空间调度中心决定是否真正移动人物。

### 27. 0.3.0-preview.22 已完成的跨世界生活交汇预言机

- 预言机在白日与晚间流线中两两检查人物，区分同屋相遇、相邻空间擦肩与同栋共振。
- 交汇强度复用现有关系引擎的来源世界、职业、性格与空间运行评分，再加入空间近接度、时段与现有关系。
- 每个候选同时校验两位人物从当前位置前往交汇空间的真实路线，不可达的场景不进入界面。
- 点选交汇只更改本地界面选择，不写入 MVU；显式点击“锁定交汇”才会生效。
- 锁定复用已有双人生活场景的原子写入、位置并发检查、事件总线、三频道草稿和经营回溯，不复制新事务逻辑。
- 锁定后两人真正进入同一空间，原有关系火花引擎将自然接手后续关系确认。

### 28. 0.3.0-preview.23 已完成的跨世界共创装修

- 已确认的双人生活场景会被编译成建筑内的共创装修项目，让人物碰撞产生可见且持久的空间结果。
- 项目同时携带两位人物的来源世界、职业、性格、视觉身份，以及目标建筑、目标空间和源场景身份。
- 生成复用统一任务中心：模拟模式按人物和房间确定性合成三案，真实模式可由酒馆助手走 Zod 结构化 AI 合同深化。
- 三种方案都会生成配色、材质、家具、照明、氛围、空间描述和后续玩法影响，并进入数字孪生前后全息投影。
- 选择方案只修改界面；确认时重新检查源关系场景、两人位置和原装修签名，避免旧方案覆盖新剧情。
- 具现后一次性更新装修、空间描述、人物状态、建筑亮点、共创事件、正文/微信/建筑草稿和经营回溯。
- 这条链路把主玩法真正闭环为“招募人物 → 发生交汇 → 形成关系场景 → 反向改变建筑 → 新空间继续承载人物生活”。

## 二、不可改变的产品原则

1. **装修和招募始终是主线玩法。** 新系统必须最终服务于“弄建筑、招人、看不同人物与世界发生碰撞”。
2. **公寓是初始自带的总部建筑。** 玩家不是从一块什么都没有的空地开始。
3. **新接管的建筑必须有基础。** 每栋建筑应自带初始格局、部分设施、原住人员或待处理问题，让玩家接手后立刻有东西可玩。
4. **经营操作与正文适度分离。** 招募、装修、建筑接管等复杂流程放进专用界面；完成后把关键结果反馈给正文，不用让正文逐步口胡每一个按钮操作。
5. **AI和代码共同完成经营。** AI负责人物、风格、故事、方案和自然语言理解；代码负责状态、校验、布局、结算、持久化和界面联动。
6. **自由不能依赖AI记住所有细节。** AI只处理“房间是什么、彼此是什么关系”；具体坐标、层级、冲突检查和渲染交给代码。
7. **先保持原样，再逐步换内核。** 底层重构不得以丢失旧功能、旧样式或降低可玩性为代价。
8. **只做服务于这张卡的黑科技。** 换一张普通角色卡就失去意义的功能，才有资格成为本项目的核心卖点。

## 三、第一优先级：必须先补好的底层能力

这些内容本身不一定显眼，但后面的多建筑、AI生成和黑科技都依赖它们。

### A. MVU 数据模型 2.0

需要重新梳理并采用官方推荐的 MVU/Zod 写法，先完整设计，再删除确实无用的字段。

主要更新：

- 增加“建筑集合”，而不是把所有状态写死为一栋公寓。
- 明确“总部公寓”“当前建筑”“已接管建筑”和“可发现建筑”。
- 给建筑、楼层、空间、租客、设施、任务和事件分配稳定 ID。
- 建立建筑、楼层、房间/科室、连接关系、占用者、装修风格和可见度等统一结构。
- 区分 AI 需要理解的语义数据与代码生成的坐标、布局和缓存数据。
- 给可选对象提供安全初始值，避免父路径不存在时更新失败。
- 减少“一处字段不完整导致整次更新报废”的脆弱校验。

之前出现的“`用户.物品栏` 不存在，无法加入急救药箱”会随着安全初始化和补父路径机制自然解决，不单独作为近期玩法任务。

### B. 统一 MVU 服务 2.0

当前服务主要负责安全读取，下一版需要成为所有新模块唯一的数据入口：

- 安全读取与订阅变化。
- 安全写入、批量更新与写入前校验。
- 自动补齐允许补齐的父路径。
- 更新前预演，失败时不给正式状态留下半成品。
- 快照和本次操作回滚。
- 把更新结果转换为统一事件，供建筑、手机、新闻和正文联动。
- 为旧脚本提供兼容层，再逐个迁移，避免一次性推翻全部代码。

### C. 统一 AI 任务服务

经营玩法不能只有固定代码，也不能让每个脚本各自随意调用 AI。需要利用酒馆助手提供的函数建立统一入口：

- 生成装修方案、建筑基础、候选租客、新闻和事件。
- 从 AI 回复中提取结构化结果，并用 Zod 校验。
- 支持排队、取消、超时、重试和错误提示。
- 区分“生成预览”和“确认写入”，避免 AI 一次输出直接污染存档。
- 记录任务来自哪个建筑、哪个房间和哪个人物。
- 让玩家能看到正在生成什么，而不是界面无响应。

### D. 真正的模块 API 迁移

现在的运行时已经能统一加载模块，但部分“能力声明”还只是清单信息。接下来要逐步把旧脚本接入正式 API：

- 新模块统一使用 `activate(context)` 和生命周期清理。
- MVU、AI、弹窗、事件、存储和日志都从服务容器获取。
- 减少模块间直接读写全局变量。
- 一个模块故障时不拖垮其他界面。
- 每迁移一个模块，都用视觉回归和功能测试确保原效果不丢。

## 四、第二优先级：多建筑经营主玩法

### 1. 总部公寓

- 现有公寓作为第一个自带建筑和经营总部。
- 保留当前二维楼层与房间玩法。
- 后续所有新系统先在总部公寓验证，再扩展到其他建筑。

### 2. 建筑接管流程

玩家可以发现并接管其他建筑，例如医院、写字楼、旅馆、商场、学校、飞船或奇幻旅店。

每次接管至少包含：

- 一份由世界观和建筑类型决定的基础蓝图。
- 已有房间/科室、初始设施、部分人员和可改造空间。
- 一段接管背景与建筑当前状况。
- 少量待玩家处理的机会，而不是强制惩罚和繁琐生存压力。
- 接管确认后才写入正式 MVU。

### 3. 通用建筑内核

不同建筑共用“楼层—空间—连接—设施—人员—状态”的底层结构，但界面和叫法随建筑变化：

- 公寓显示房间、租客和公共区。
- 医院显示科室、病房、员工和患者。
- 写字楼显示部门、办公室、员工和访客。
- 飞船显示舱段、系统、船员和乘客。

这样既保持自由，也不要求 AI 理解像素坐标。

### 4. 独立装修中心

- 在专用界面选择建筑和空间。
- 让 AI 生成多个装修方向，玩家选择、编辑和确认。
- 代码计算空间占用、设施归属和最终状态。
- 完成后把装修结果、人物反应和可用场景回传正文。
- 保留爽文节奏，不把经营变成材料税、工期税和失败惩罚模拟器。

### 5. 独立招募中心

- 按当前建筑、世界观、已有租客和玩家要求生成候选人。
- 支持来自其他作品、世界或原创设定的人物。
- 展示候选人的身份、需求、可分配空间和可能产生的碰撞点。
- 玩家确认后，统一创建租客实体、联系方式、门牌和建筑位置。
- 招募结果进入正文、微信、掌上建筑和后续事件系统。

### 6. 逐步感知

- 未发现的建筑、楼层、房间和人物信息不应一开始全部公开。
- 随接管、探索、装修、对话和事件逐步解锁。
- “未知”是可玩的悬念，不是阻止玩家行动的硬门槛。

## 五、第三优先级：房东模拟器专属黑科技

### 1. 建筑界面编译器

输入同一种建筑数据结构，自动生成不同建筑类型的专属经营界面。它是多建筑玩法最先应该实现的黑科技，也是后续数字孪生的基础。

### 2. 建筑数字孪生

把现有二维掌上公寓升级为可缩放、可旋转、可分层查看的 2.5D 建筑视图：

- AI只提供楼层、房间类型、大小和邻接关系。
- 代码负责自动排布、坐标、视角和动画。
- 人物、房间状态、装修和事件可以直接显示在建筑中。
- 同一套系统可以渲染公寓、医院、写字楼和异世界建筑。

### 3. 装修具现化引擎

把 AI 的自然语言装修方案转换成可执行的风格、家具、材质、配色、照明和空间标签，再由代码生成装修卡片、缩略图和数字孪生变化。重点是“方案真的改变建筑”，而不是只生成一段描述。

### 4. 叙事—空间同步

从最新正文中提取“谁到了哪里、做了什么”，与真实建筑结构核对，然后更新人物在建筑中的位置和状态：

- 合法移动直接进入待确认更新。
- 与实际格局冲突的内容进入冲突队列。
- 不让一段口胡直接破坏 MVU。

### 5. 建筑神经系统

让同一个事件同时影响多个现有系统。例如医院停电后：

- 建筑界面显示受影响区域。
- 新闻出现报道。
- 微信出现租客或员工消息。
- 人物行为和正文获得同一事件上下文。
- 修复后所有模块收到同一结果。

这会让天气、新闻、微信和掌上建筑从多个独立小玩具变成同一个活世界。

### 6. 租客具身化引擎

每个租客拥有稳定身份，并在所有界面保持一致：头像、颜色、门牌、联系人卡片、建筑标记和事件记录都指向同一个人物实体。它能明显强化“这是我招进来并安置在这里的人”的感觉。

### 7. Landlord OS

把现有界面组织成只属于这张卡的“房东经营系统”，而不是通用角色卡后台：

- 建筑管理窗口和多任务切换。
- 招募、装修、AI生成任务中心。
- 建筑、租客、事件和世界包的统一搜索。
- 当前模块、MVU和联动状态的可视化。
- 版本与扩展包管理。

窗口系统、命令面板、状态观察等通用技术可以作为底层，但展示出来的每一项都必须围绕房东、建筑和租客。

## 六、世界书、开场白与扩展内容

### 保持角色卡原生携带

- 核心世界书。
- 默认开场白和基础备用开场白。
- 保证角色卡离线导入后立即可玩。

### 后续可由脚本显式安装

- 新建筑包。
- 新世界观包。
- 特殊租客来源包。
- 主题装修包。
- DLC 世界书和配套开场白。

这些内容应由玩家在创意工坊或版本中心主动选择安装，带唯一名称、版本号、缓存和回滚。启动时静默覆盖世界书或开场白不列入计划。

## 七、测试与发布必须同步更新

每个阶段都必须同时维护在线版和离线版，并至少验证：

- 总部公寓初始状态正确。
- 接管第二栋及更多建筑。
- 装修、招募的生成预览、确认和取消。
- 刷新或重开聊天后状态仍然正确。
- CDN 加载成功与失败时的提示。
- MVU 非法更新不会破坏现有状态。
- 正文、微信、新闻和建筑事件不会互相矛盾。
- 原有关键界面没有样式缩水。

所有构建、测试和验收都在本地 Mac 与允许的本地环境完成，不使用 GitHub Actions。

## 八、明确延期，不挤占当前主线

- 大富翁迁移和重制。
- 音乐系统的进一步增强。
- 为所有角色卡服务的通用插件平台。
- 只有“看起来像终端”但不改变玩法和数据的伪黑科技。
- 启动时静默远程修改世界书或开场白。
- 与玩法无关的 localStorage 清理，不作为近期优先级。
- Z5.20 旧存档迁移与兼容；当前阶段按新版角色卡、新聊天重新开始设计。

## 九、建议开发顺序

### 里程碑 1：多建筑地基

1. 完成 MVU 数据模型 2.0 草案。
2. 完成统一 MVU 服务 2.0。
3. 完成统一 AI 任务服务的最小闭环。
4. 保持总部公寓正常运行。
5. 用一栋医院和一栋写字楼作为通用建筑模型测试样例。

**验收结果：** 新版角色卡能安全保存多栋不同建筑，总部公寓正常运行，AI生成结果必须经过预览和确认。

### 里程碑 2：建筑经营中心

1. 完成建筑界面编译器第一版。
2. 完成建筑接管流程。
3. 完成独立装修中心和招募中心。
4. 完成逐步感知。
5. 把操作结果反馈到正文和微信。

**验收结果：** 玩家能在不拖慢正文的情况下接管、装修和招募，并看到跨世界人物进入不同建筑。

### 里程碑 3：建筑真的“活起来”

1. 装修具现化引擎。
2. 建筑数字孪生。
3. 租客具身化。
4. 叙事—空间同步。
5. 建筑神经系统。

**验收结果：** 建筑、人物、正文、微信、新闻和事件共享同一份真实状态，不再只是几个互不相干的界面。

### 里程碑 4：Landlord OS 与扩展生态

1. 用 Landlord OS 统一组织已经成熟的经营功能。
2. 扩展创意工坊，支持建筑包、世界包、租客包和装修包。
3. 加入显式版本安装、缓存、回滚和兼容提示。
4. 在不破坏离线可玩的前提下优化在线更新体验。

**验收结果：** 玩家感受到的是一套完整的房东经营系统，而不是一堆零散酒馆助手脚本。

## 十、当前下一步

多建筑地基和经营中心第一切片已经落地。下一轮不应立刻制作 2.5D 大楼，也不应继续堆零散功能。最合理的起点是：

> **先把本地模拟任务服务扩展成“本地/AI 双模式”的统一任务中心，再做建筑事件总线与正文/微信的结果反馈。**

这一步完成后，现有医院、写字楼、装修中心和招募中心就能在不改变界面流程的前提下接入真实生成，同时开始把天气、新闻、微信和建筑动态连成同一个世界。

### 29. 0.3.0-preview.24 已完成的真实宿主闭环
